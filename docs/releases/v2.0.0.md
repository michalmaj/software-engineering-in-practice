## Release body (paste as-is)

## Software Engineering in Practice — v2.0.0: Three Fully Supported Language Tracks

Python, Go, and Java are now three equal, independently audited,
**fully supported** tracks through this course — not one primary
language with two examples alongside it. This is the change that
makes this a major version.

### What "fully supported" means here

For each of the three tracks: the full Labs 05-30 path, the same
learning outcomes, real working starters, correct run/test commands,
project continuity session to session, a supported capstone path, and
a technical + pedagogical + EN/PL editorial audit — with no known open
BLOCKER or unresolved MAJOR finding. It does **not** mean identical
line counts or architecture across languages, that a student installs
all three toolchains, that every lab is guaranteed to fit 90 minutes
for every student, or that every operating system combination was
hand-tested. Those distinctions matter and are kept explicit in this
course's maintainer documentation.

### What's in this release

- **30 lab sessions, 90 minutes each**, told as one continuous story
  from a first terminal session to handing a project to another team.
- **Full English and Polish materials** for every lab, kept in parity
  by an automated structural check (heading structure, matching
  executable code blocks) on every push.
- **Three independently verified language tracks** — Python, Go, and
  Java — real, working starters across every act, not transliterated
  copies of each other.
- **Local-first onboarding**: `START-HERE.md` walks a complete
  beginner through installing Git and VS Code and getting the
  repository open, on Windows (Git Bash), macOS, or Linux, before any
  language toolchain is needed. GitHub Codespaces remains available as
  an explicit alternative for anyone who'd rather not install anything
  locally.
- **Order API (Labs 21-25)**: an HTTP service built incrementally
  across all three languages — request/response contracts, SQLite
  persistence that survives a schema change, bounded retry around an
  unreliable external call, structured operational logging, and a
  real two-release workflow (`v1.0.0` tagged at the end of Lab 24,
  `v1.1.0` — an additive, backward-compatible `priority` field — at
  the end of Lab 25).
- **TableTime capstone (Labs 26-30)**: a five-session team project —
  kickoff and planning, iterative development against a real MVP,
  a change request with impact analysis done before implementation, a
  production incident handled without abandoning the normal
  engineering workflow, and a realistic fork-and-PR handover to
  another team.
- **Hardened Course Health and CI**: the same checks this repository's
  own CI runs on every push now also run against the public starters
  a student actually forks, catching regressions before they reach a
  classroom.
- **A completed editorial and technical audit cycle**: every one of
  the 60 lab README files (EN + PL) was read in full and verified
  hands-on, not sampled, across a sequence of focused audits.

### What changed since v1.1.0

The single biggest classroom-fit problem found after `v1.1.0` was Lab
25 carrying two full release cycles in one 90-minute session — a
near-certain overrun, most acute in Go and Java. This release resolves
it structurally, not by cutting scope: the first release (`v1.0.0`)
now ships at the end of Lab 24, alongside that lab's own logging work,
and Lab 25 does exactly one release cycle from there. No lab was
added, no learning outcome was removed, and the test this course's own
authors once got wrong — a historical database row with a genuinely
`NULL` value that must still map to a sensible default — is unchanged
in all three languages.

### Known, disclosed limitations

This release does not claim more certainty than the evidence supports:

- **Windows GUI**: a real Windows GitHub Actions smoke test runs this
  course's shared Git Bash command sequence on genuine `windows-latest`
  runners on every push. A complete manual walkthrough of a fresh
  Chocolatey install, UAC prompts, and VS Code's terminal-profile
  dropdown on real Windows 11 hardware has not been performed.
- **GitHub collaboration**: the paired-review and fork-based handover
  exercises were verified with real Git mechanics in local
  repositories simulating two sides of a pull request, not a complete
  walkthrough using two independent GitHub accounts end to end.
- **90-minute timing**: every per-lab timebox in this course's
  maintainer documentation is an expert estimate built from hands-on
  walkthroughs of the actual lab text, not a measurement of real
  beginner students' working time. Java's Lab 24 specifically carries
  a disclosed, tight margin (roughly 60-90 minutes for a beginner) —
  not because Java has less material, but because it already carries
  this course's heaviest per-track logging setup, with a new release
  step now layered on top. A student or instructor hitting this should
  expect to need a checkpoint, not read it as a sign something is
  broken.

### Start here

New to this course? Start with
[`START-HERE.md`](../../START-HERE.md) — it walks you through
installing Git and VS Code and opening this repository locally,
assuming no prior terminal, Git, or GitHub experience. You won't need
a language toolchain until Lab 05, where you install the one language
you pick.

Prefer not to install anything locally? GitHub Codespaces remains a
supported alternative — see the `README.md` section on Codespaces.

See [`README.md`](../../README.md) for the full course map and setup
details.

## Polski

## Software Engineering in Practice — v2.0.0: Trzy w pełni wspierane ścieżki językowe

Python, Go i Java są teraz trzema równorzędnymi, niezależnie
zaudytowanymi, **w pełni wspieranymi** trackami w tym kursie — nie
jednym głównym językiem z dwoma przykładami obok niego. To jest
zmiana, która sprawia, że to wydanie główne.

### Co oznacza "w pełni wspierany"

Dla każdego z trzech tracków: pełna ścieżka Labów 05-30, te same
efekty nauki, prawdziwe działające startery, poprawne komendy do
uruchamiania i testowania, kontynuacja projektu między zajęciami,
wspierana ścieżka capstone oraz audyt techniczny, dydaktyczny i
redakcyjny EN/PL — bez znanych otwartych BLOCKER-ów ani
nierozwiązanych MAJOR-ów. To **nie** oznacza identycznej liczby linii
kodu czy architektury między językami, instalacji wszystkich trzech
toolchainów przez studenta, gwarancji, że każdy lab zmieści się w 90
minutach dla każdego studenta, ani ręcznego testu każdej kombinacji
systemu operacyjnego. Te rozróżnienia mają znaczenie i są wyraźnie
zachowane w dokumentacji dla opiekunów kursu.

### Co jest w tym wydaniu

- **30 sesji laboratoryjnych po 90 minut**, opowiedzianych jako jedna
  ciągła historia od pierwszej sesji w terminalu do przekazania
  projektu innemu zespołowi.
- **Pełne materiały angielskie i polskie** dla każdego labu,
  utrzymywane w parytecie przez automatyczną kontrolę strukturalną
  (struktura nagłówków, zgodne bloki kodu wykonywalnego) przy każdym
  push.
- **Trzy niezależnie zweryfikowane ścieżki językowe** — Python, Go i
  Java — prawdziwe, działające startery w każdym akcie, nie
  transliterowane kopie siebie nawzajem.
- **Lokalny onboarding jako domyślna ścieżka**: `START-HERE.pl.md`
  prowadzi kompletnego początkującego przez instalację Git i VS Code
  oraz otwarcie repozytorium lokalnie, na Windows (Git Bash), macOS
  albo Linux, przed tym, jak jakikolwiek toolchain językowy jest
  potrzebny. GitHub Codespaces pozostaje dostępną alternatywą dla
  każdego, kto nie chce niczego instalować lokalnie.
- **Order API (Laby 21-25)**: usługa HTTP budowana przyrostowo we
  wszystkich trzech językach — kontrakty żądanie/odpowiedź, trwałość
  SQLite przeżywająca zmianę schematu, ograniczony retry wokół
  niestabilnego wywołania zewnętrznego, strukturalne logowanie
  operacyjne i prawdziwy dwuwydaniowy workflow (`v1.0.0` otagowane na
  koniec Lab 24, `v1.1.0` — addytywne, kompatybilne wstecz pole
  `priority` — na koniec Lab 25).
- **Capstone TableTime (Laby 26-30)**: pięciosesyjny projekt zespołowy
  — kickoff i planowanie, iteracyjny rozwój wobec prawdziwego MVP,
  change request z analizą wpływu wykonaną przed implementacją,
  incydent produkcyjny obsłużony bez odchodzenia od normalnego
  workflow inżynierskiego oraz realistyczne przekazanie projektu przez
  fork i PR innemu zespołowi.
- **Utwardzony Course Health i CI**: te same kontrole, które CI tego
  repozytorium uruchamia przy każdym push, działają teraz również na
  publicznych starterach, które student faktycznie forkuje, wychwytując
  regresje przed tym, jak dotrą do sali zajęć.
- **Zakończony cykl audytu redakcyjnego i technicznego**: każdy z 60
  plików README laboratoriów (EN + PL) został przeczytany w całości i
  zweryfikowany praktycznie, nie wyrywkowo, w serii skoncentrowanych
  audytów.

### Co się zmieniło od v1.1.0

Największym problemem dopasowania do zajęć znalezionym po `v1.1.0`
było to, że Lab 25 nosił dwa pełne cykle wydania w jednej 90-minutowej
sesji — prawie pewne przekroczenie czasu, najbardziej dotkliwe w Go i
Javie. To wydanie rozwiązuje to strukturalnie, nie przez ograniczenie
zakresu: pierwsze wydanie (`v1.0.0`) jest teraz tagowane na koniec Lab
24, razem z pracą nad logowaniem w tym labie, a Lab 25 wykonuje od
tego punktu dokładnie jeden cykl wydania. Nie dodano żadnego labu, nie
usunięto żadnego efektu nauki, a test, który autorzy tego kursu sami
raz popełnili błędnie — historyczny wiersz bazy danych z naprawdę
`NULL` wartością, która musi wciąż mapować się na sensowną wartość
domyślną — jest niezmieniony we wszystkich trzech językach.

### Znane, jawnie ujawnione ograniczenia

To wydanie nie twierdzi więcej, niż pozwalają na to dowody:

- **Windows GUI**: prawdziwy test dymny GitHub Actions na Windows
  uruchamia wspólną sekwencję komend Git Bash tego kursu na
  prawdziwych runnerach `windows-latest` przy każdym push. Kompletny
  ręczny przegląd świeżej instalacji Chocolatey, okien UAC i listy
  profili terminala VS Code na rzeczywistym sprzęcie z Windows 11 nie
  został wykonany.
- **Współpraca na GitHubie**: ćwiczenia z parowanego review i
  przekazania projektu przez fork zostały zweryfikowane prawdziwą
  mechaniką Gita w lokalnych repozytoriach symulujących obie strony
  pull requesta, nie kompletnym przejściem z dwoma niezależnymi
  kontami GitHub od początku do końca.
- **Czas 90 minut**: każdy limit czasu dla labu w dokumentacji dla
  opiekunów kursu jest estymacją ekspercką zbudowaną na praktycznych
  przejściach przez rzeczywisty tekst labu, nie pomiarem rzeczywistego
  czasu pracy początkujących studentów. Lab 24 w Javie nosi jawnie
  ujawniony, ciasny margines (około 60-90 minut dla początkującego) —
  nie dlatego, że Java ma mniej materiału, ale dlatego, że już niesie
  najciężniejszą konfigurację logowania w tym kursie, na którą teraz
  nakłada się nowy krok wydania. Student albo prowadzący, który na to
  trafi, powinien oczekiwać potrzeby checkpointu, nie odczytywać tego
  jako znak, że coś jest zepsute.
